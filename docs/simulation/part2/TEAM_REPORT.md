# 第二阶段队会汇报（五页）

## 第 1 页：阶段目标与当前结论

标题：自己的地图场景已经接通真实点云和现有规划器

讲述：在第一阶段手动运动和真值定位基础上，实现“打开场地—手动移动—看点云对齐—RViz 点目标—看规划结果”。
机器人仍由键盘控制，没有自动跟踪、自动到点或真实定位。
本次场地是二维占据轮廓的简化挤出，不能作为比赛场地三维复原或碰撞动力学验收。

结论：M0 雷达与 M1 地图一致性通过；M2 展示链路工作，但严格轨迹检查 6/15 通过，
因此第二阶段尚不能宣布整体通过。下一步先解决段间连续性。

## 第 2 页：系统链路

~~~text
Gazebo 场地 + 机器人
  ├─ 真值状态 → 速度安全适配 → /localization/odometry + TF
  └─ gpu_lidar → bridge → /sim/lidar/points
                        → 过滤、测量时刻 TF → /filted_topic_3d + /aligned_points

原地图 + 真值定位 + 点云 + RViz /goal → 现有规划器
                                  → TrajectoryPoly + 原有 Marker → RViz
键盘 → 超时、限幅保护 → Gazebo 运动（没有自动跟踪）
~~~

讲述：ROS domain 26，统一仿真时间，缺少对应时刻 TF 就丢帧。
使用真实传感器回波，地图显示不是点云来源。没有同时启动 fixture、HDL、Point-LIO 或 MCU。

## 第 3 页：场景与地图对齐

展示：evidence/stage2-planning.png，左 Gazebo、右 RViz；再显示地图验收表。

数据：400×400、0.05 m、20×20 m，下界 (-13.394,-12.079)。
15,590 个原始占据格合并为 2162 个几何体，逐格比较 160,000 格、差异 0。
三个地标误差 0，真实云到占据格中心距离 P95 约 3.8 cm。
测距另用已知平面墙面验证，移动/旋转后的最大误差约 1.01 cm。

讲述：只挤出原始占据区域，安全膨胀仍交给规划器；保留三张原地图和哈希。
1 m 障碍高度不代表真实 BEV 地形。

## 第 4 页：现场演示与实测指标

播放 demo.mp4（89.8 秒），或按 README 现场启动：
旋转机器人 → 短距离前进 → 看橙色点云变化 → 点击 RViz 2D Goal Pose → 看真实轨迹。

讲述：软件渲染下双 GUI 运行 310 秒，实时率约 1.00，点云 5 Hz；
RSS 采样峰值约 1.49 GiB，CPU 约占 4 核容量 89%，后续加控制和定位还要重测。
第一阶段 34 项回归通过；暂停无过期运动，停止无遗留发布者，重启只有一辆机器人。

必须补充：画面上出现路径不等于轨迹已经安全可跟踪。

## 第 5 页：问题与下一步

第一优先：15 次均有轨迹、端点误差均小于 6 mm、已采样点没有碰占据区，
但 9 次存在段间跳变，最大约 11.9 cm，严格路径验收不通过。
原因候选是最终时长与多项式系数不同步，需对最终时间重求系数并做连续性回归。
原计划不改核心算法，当前未擅自扩大范围。

第二优先：RViz 一次退出内存错误；没有残留进程、可重启，但仍需根因排查。
保留 GLSL、EGL、Qt 和 MINCO 警告，不把它们从报告中隐藏。

进入第三阶段前：修复连续性、重跑五组各三次，再验证速度坐标、控制切换、限速、
停车与仿真暂停、计算负载和到点判据。详细清单见 HANDOFF.md。
队内汇报口径：“点云和规划展示链路已打通，发现并量化了轨迹连续性问题，尚未进入自动跟踪。”
